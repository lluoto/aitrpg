## 二、语音层对每条消息要回答的四个问题

| 问题 | 现状 | 判定 |
|---|---|---|
| 该不该念？ | `type`：`system` / `action` 不念，`narration` / `dialogue` 念 | 够用 |
| 谁来念？ | `speaker`（"KP" / NPC 名 / "守秘人"） | 够用 |
| 预渲染还是实时合成？ | `verbatim`：为真表示模组原文逐字输出，内容固定、可离线预合成 | 够用 |
| 用什么情绪念？ | `NPCAgent` 持有 `mood`，但**消息上没有** | **缺** |

## 三、唯一的缺口：情绪不随消息传递

`NPCMood` 有 8 个取值（`neutral / friendly / angry / fearful / suspicious / excited / sad / calm`，见 `src/agent/types.ts`），与主流情感 TTS 的 style 参数几乎一一对应，是现成的音色控制输入。

问题在于它停在 `NPCAgent` 内部。API 出口 `src/api/server.ts` 的 NPC 对话分支只传了三个值：

```ts
session.addMessage(npcName, reply, "dialogue");
```

**不能在播放时回查 `npcAgent.getMood()`**：情绪是会变的状态机（8 种触发驱动转移），播放时刻的情绪未必是说这句话时的情绪；历史回放更是必然错位。情绪必须在消息生成的那一刻固定下来。

### 建议的改法

不要再往 `addMessage` 加第七个位置参数——它已经有六个了。应当把尾部的可选参数收成一个 options 对象：

```ts
addMessage(speaker, content, type, opts?: {
  visibility?: VisibilityRule;
  discoverer?: string;
  verbatim?: boolean;
  mood?: NPCMood;
})
```

这会动到 `addMessage` 的全部调用点，属于一次独立的小重构，**应当在当前进行中的真相源迁移落地之后再做**，避免在同一个文件里叠加两份未完成改动。

## 四、合成分层

模组文本的性质不同，合成路径也应不同。三层：

| 层 | 内容 | 合成方式 | 判据 |
|---|---|---|---|
| 预制 | 模组开场白、朗读文本 | 离线批量合成，可上真人配音 | `verbatim === true` |
| 实时 | KP 即兴叙述、NPC 台词 | 流式合成，句级切分 | `type` 为 `narration` / `dialogue` 且非 verbatim |
| 不念 | 骰点结果、状态变更、系统提示、模组元信息 | 不合成 | `type` 为 `system` / `action` |

预制层是免费的延迟优化：内容在加载时就已确定，等于把这部分的合成延迟降为零。

实时层的关键不是选哪家快，而是**必须流式**。中文叙述约 4 字/秒，一个 100–400 字的回合是 25–100 秒音频；按实测 RTF 0.28–0.5，整段合成要等 7–50 秒，不可用。流式下用户只等首包（国内可直连的几家在 150–300ms），而 RTF < 1 保证播放不会断流。

## 五、舞台指示：现在不用处理，但要知道

NPC 台词按提示词第 7 条要求带括号舞台指示：

> 用小括号括起的动作/神态/语气描写开头或穿插（如（抬眼打量他们）（声音低沉）（指尖敲着桌面））

这些**不能直接送进 TTS**，否则会把「抬眼打量他们」当台词念出来。

但现在不需要动它：格式是一致的（中文全角括号），信息没有丢失，未来写一个纯函数切分即可。而且这些指示不该被丢弃——它们恰恰是最好的韵律提示，`（声音低沉）` 对应降低音高、放慢语速，比单一的 mood 标签更精细。

注意：现有的括号剥离只处理 NPC **姓名后缀**（`菲碧·特里坎（母亲）` → `菲碧·特里坎`），与台词内的舞台指示无关，不要混淆。

### 第 2 步做完时发现的事

接上 `mood` 之后实跑一次 NPC 对话，`/history` 里拿回来的是 `paranoid` —— 不在
`NPCMood` 八个取值里。根因是模组内联人格把 `initialMood` 声明成了裸 `string`；
收紧类型后一共翻出六个：`paranoid`、`hostile`、`anxious_hopeful`、`playful`、
`paralyzed_terrified`、`alien_calm`。

它们不会报错，只会让下游每个分支都落空——语音层选不到音色。这类值已按语义映射回
八值集，原标签留在注释里；`traits` 本来就承载了大部分细节（瘫痪在 `stability: 1`、
非人感在 `friendliness: 1`、活泼在 `curiosity: 9`）。

情绪另有三个不经编译器的入口：`npcs.yaml` 运行时解析、编辑器存的模组 JSON、
以及历史数据库行。现由 `asNPCMood()` 在人格进入系统的那一点统一收口。

**教训**：把类型收紧只能管住仓库里的数据，管不住运行时喂进来的。两件事都要做。

## 七、一条经验

本文的判断有一处是被实测纠正过的：此前曾推断「KP 会把模组原文照抄进叙述」，据此准备改提示词。实测 5 个场景，KP 叙述对原文的 8-gram 重合率平均 6.9%、最长逐字片段 13.4 字——它在正常改写，推断不成立，提示词未改。

真正逐字输出的是模组开场白，走的是不经 LLM 的直出路径，这才是 `verbatim` 标记要解决的对象。

**对语音的直接含义**：不要按「模型可能会怎样」设计音频管线，要按消息的实际来源设计。来源是可判定的（是否经过 LLM），模型行为是需要实测的。
