# 事故记录：2026-08-07 UTF-8 损坏（已闭合）

## 一、这是什么事故

2026-08-07，`src/api/server.ts`（及少量同批文件）在写盘过程中被破坏成非法
UTF-8：中文字符被替换成 `U+FFFD`（替换字符）加问号，部分行还被粘连成一行。
取证与修复过程产生的原始材料（字节级对照、修复脚本、外部模型的分析报告）
留档在 `analysis/archive/2026-08-07-utf8-corruption/`（该目录随 `analysis/`
一起被 `.gitignore` 排除——见下方「关于取证目录不入库」）。

**事故已闭合。** 可复验的判据：全仓 `src/**/*.ts` 的 `U+FFFD` 计数为 0
（2026-08-29 复核）。要自己复验，跑一段扫描当前 `src/` 树里的 `\uFFFD` 计数
即可，不需要额外脚本——取证目录里留的是修复过程的原始材料，不是复验本身
依赖的东西。

## 二、机制（唯一有前向价值的部分）

抄自取证目录里 `server_repair_v2.py` / `server_split_fix.py` 的文件头
（原文是英文，这里照译）：

> 3 字节 UTF-8 字符的**末字节**被替换成 `'?'`；紧随其后的一个 ASCII 字节
> **被吞掉**。如果被吞的是 `'\n'`，两行就会粘连成一行。

也就是说，这不是"编码声明错了"（不是 GBK/UTF-8 混淆那类常见问题），而是
**写盘管线本身在字节层面丢字节**——一个多字节字符写坏，连带吃掉了它后面
紧挨着的一个字节。这解释了为什么修复不能靠简单的"重新声明编码"或"整体
转码"完成：损坏是逐处、不规则的，只能按字节比对原文逐条修复（取证目录里
那些 `_server-*.txt`/`_clean-*.txt` 就是这个比对过程的中间产物）。

已知这条机制目前唯一在本仓复现过的触发场景：**中文源文件经 PowerShell
写入**（`Set-Content` 等）。这正是 `docs/todo.json` 里 `todo-14`
（"本仓源文件不能过 PowerShell 写，`Set-Content` 会把中文 mojibake"）这条
规矩的证据来源——那条规矩不是凭空定的，是这次事故留下的教训。

## 三、关于取证目录不入库

`analysis/` 整体在 `.gitignore` 里（`git check-ignore -v analysis/` 确认过），
所以 `analysis/archive/2026-08-07-utf8-corruption/` 下的 17 个原始文件
（两个修复脚本 + 一份外部模型分析报告 + 十四份字节级比对中间产物）**不会
随仓库一起被克隆**。这份 README 因此放在 `docs/`（会入库），正文里指向那个
不入库的目录——`analysis/` 下的东西本来就是"能由一个点得出名字的脚本重跑
再生"的产物（`preflight.ts` 第 10 项对这类引用的判断口径也是如此，见该脚本
注释），事故本身的记录与复验判据（本文件 + 全仓 U+FFFD=0）才是需要跟着
仓库走的部分；字节级修复过程的中间产物不需要。
