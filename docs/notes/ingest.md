### pdf-parse 的坑（会浪费掉半小时，先看这条）

依赖是 **v2.4.5**，导出的是 `PDFParse` **类**，不是网上示例里那个默认函数。
`require("pdf-parse")(buffer)` 会抛 `pdfParse is not a function`——
它在 `package.json` 里长期没人用，多半就是卡在这里。正确用法：

```ts
const { PDFParse } = require("pdf-parse");
const res = await new PDFParse({ data: buffer }).getText();
// res.total → 页数；res.text → 全文；res.pages[] → 逐页
```

`getText()` 之外还有 `getPageTables` / `getImage` / `getHyperlinks` 等，
模组附件是 6 张图，将来要用得上。

**清洗**（`cleanPageText`）判断"换行是排版造成的还是句子结束"，靠四个信号：句子终止标点、
终止标点后的右引号（场景描述整段是引文，只认句号会把描述和 KP 说明粘住）、`▶` 条目标记、冒号。
冒号需要两条规则：冒号结尾的行引出下面整块内容（不能把内容拽上来），
而**短**的冒号结尾行是场景名（不能被上一段吸走）——区分两者只有长度这一个信号。

### p15 的结局与奖励表被整片焊成一行（潜伏，待修）

`cleanPageText` 在第 15 页把 **24 行压成 4 行**（全书最高压缩比），其中第 4 行是个
400+ 字的团块，把 **4 段结局叙述 + 3 个结局标签 + 整张 9 行奖励表**全焊在一起：

```
…"伎俩"呢...Good End调查员在发现…照顾爱莉吧...Bad End调查员在中控室…
True End调查员找到了…杀死所有受害者 San 削减 d6解救受害者 San 值回复…委托达成 信誉+10…
```

第 3 行同样坏了：`Normal End调查员没有知道事情的真相…` —— 标签把自己名下的叙述吸了进来。

**主因不是 ASCII 省略号**（那只是让 `Good/Bad/True End` 被前一行吸走的那一个因素）。
主因是 `shouldJoin` 的默认假设：「中文正文里，一行结束而没有终止标点，几乎总是被栏宽切断的」。
这条对中文散文成立，对 p15 的两类行不成立：

- **纯拉丁标签**：`Normal End` / `Good End` / `Bad End` / `True End`
- **以骰子或数值收尾的表格行**：`杀死所有受害者 San 削减 d6`、`委托达成 信誉+10`

**今天下游影响是零**：`ModuleData.endings` 与奖励都还没抽，没人读 p15。
所以这是潜伏损坏。但它是「做结局那一轮」的必经障碍——那一轮开工第一件事就是这个。

1. 给判据加一条共同要求：**上一行以终止标点收尾**。手判这 6 个假阳全部能排掉

3. 承认它是语义判断，交给 LLM——与根因 B、物品/线索边界同一类。

**跨页连接**（`joinPages`）复用同一个判据，但**多一道页边界专用的否决**：页首行以冒号收尾时
一律不接，不看长度。因为页内那条长度规则的前提是「长的冒号行通常是正文」
（`艾德里安会在外围布置 3 种陷阱：`），而页首那一行有标题先验。
不加这道否决就会出真事故：p1 末行以 ASCII 省略号 `....` 收尾（`SENTENCE_END` 只认 U+2026 的 `…`），
p2 首行是 21 字的 `事件真相（想跑的人请不要继续往下看了。）：`，两条守卫同时失效，
把一个小节标题焊到了上一页正文末尾。**这个错接在 6 处接续里占 1 处，最初没被发现，
因为当时只核了「跟在 `▶` 后面」的那 4 处，把多出的 2 处当成分母差异解释掉了。**

**校准器**（`diffValues` / `formatDiff`）逐字段比对两份 `ModuleData`，产出 missing/extra/changed 三类。
带 `id` 的数组按 id 配对而非下标——生成物的场景顺序不必与手写那份一致，
按下标比会把"顺序不同"报成"每项都不同"，真实差异被噪音埋掉。实测：真实模组自比零差异；
把候选截到 3 个场景并倒序，只报 17 处缺失，无一条顺序误报。

**章节切分**（`sectionize`）吃清洗后的逐页文本，产出带层级的块：标题 + 正文 + `▶` 条目。
层级不能拍平——`▶捕兽夹` 属于「农场外围」，扁平之后陷阱不知道该挂哪个场景，
引擎里那对单数的 `support.trapSceneId`/`trapClueId` 正是这么来的。
每个块与条目都带 `{page, line}`，供 `Provenance.sourceRef` 使用。

有一类行既像条目又像标题（`▶证物室：` 冒号后无内容，底下再挂真条目），
按原文语义它是小节标题，`▶` 必须剥掉，否则场景名成了 `▶证物室`，与基准对不上。

**端到端实测**（PDF → 清洗 → 切分）：切出 44 块 / 39 条目，
**基准的 20 个场景名 20/20 全部命中**。多出的标题是文档结构（前言/附录/写在最后）、
NPC 小节（菲碧·特里坎/米尔·特里坎，基准里确实是 NPC）与子小节，只有「与背景」「可选」两个像误检片段。

**基准规模**（读取模块要还原的目标量）：20 场景 / 11 NPC / 10 物品 / 4 结局 / 32 线索。

### 已验证行不通：靠引文判定场景（别再试了）

场景描述大多以整段朗读引文开头（`农场主别墅：“从远处观察别墅…”`），
看上去是个现成的判据。**实测不成立**：命中 15 / 误报 6 / 漏报 5（基准共 20 个场景）。

- 漏报：`报亭`、`与艾德里安的会面`、`证物室`、`农场外围`、`谷仓形建筑` —— 真场景，但没有朗读引文
- 误报：`敌对神话生物`（附录里的米戈描述）、`比较大的奇怪管道`、`艾米丽与爱莉的棺材`；
  其中 `旅店` 有引文也确实像个地点，可能是基准自己漏收了

结论：**「这一块是不是场景」是语义判断，不是文本形态能定的**，应归 LLM 那一层。
确定性部分能做的是把 44 个块连同标题、正文、条目、`{page,line}` 一并交出去，
分类留给语义层——这与「规则管死板形态、LLM 管理解」的分工一致。

改用 LLM 之后：**命中 20 / 误报 7 / 漏报 0**，严格优于引文启发式的 15/6/5。
7 个误报大多站得住（`旅店` 确实是地点，`绑架犯的报道` 是子场景），可留给人工过一遍。

**踩过的坑（值得记）**：prompt 里把标题展示成 `【农场外围】`，模型就照这个格式返回键
`"【农场外围】"`。解析器拿裸标题匹配，43 条全被丢弃，表现成"模型没干活"——
实际它全做对了。**展示格式不该变成输出格式的契约**，解析侧要做键归一化。
诊断方法是把原始响应打出来看，别猜。

> 再遇到「模型没干活」这个症状，**先量 `maxTokens`**：回复被截断的表现与上面这个键格式坑
> 一模一样，而 43 块一次性送进去全靠 `.env` 把它抬到了 256000（见上面 LLM 可用性那条）。
> 两个原因看起来一样，查错方向完全相反。

> 以减轻运行期压力（装载等待可接受）。`generate-llm-expanded.ts` 已有
> 「已存在 llmExpanded 就跳过」的语义，是现成的接入点——把它从运行期挪到构建期即可。

### id 是内部句柄，不与基准对齐（2026-08-19）

基准的场景 id 是带上下文的人工意译：`霍姆斯医院 → hospital`（人名丢了）、
`与艾德里安的会面 → adrian_hospital_meeting`（反而加了原标题没有的 hospital）、
`证物室 → police_evidence_room`（补了父场景前缀）。这是语义翻译，机械复现不了；
把基准 id 塞进 prompt 当范例又等于泄题，测出的命中率不说明任何事。

所以生成的 id 只保证唯一、同一 PDF 重跑稳定、纯 ASCII、可被 `targetSceneId` 解析，
形态是 `scene_NN`（按**块**编号，不按场景——分类结果一变，按场景编号会让所有 id 集体挪位）。
配对改由 `diffValues(..., { pairBy: ["id","name"] })` 承担：先按 id 配，配不上按 name 配，
id 不同的单列成 `id-mismatch`，不去污染 changed 那个计数。实跑 17 处 id 不一致，全部是这种情况。

顺带修掉校准器一处会埋掉信息的地方：`allHaveKey`（当时叫 `allHaveId`）原本要求数组非空，
于是候选侧 `clues: []` 会把整个数组拖回按下标比，基准全部 32 条线索都印成
`clues[0]`、`clues[1]` 这种纯下标路径（每个场景各自从 0 数起，最多到 `clues[3]`），
既看不出缺的是哪条，也没法直接拿去干活。空数组现在平凡成立，路径变成
`scenes[维森酒吧].clues[clue_bar_ask_around]` —— 这份清单直接是下一轮的路线图。

### connections 不是抽取活，是结构推断活（2026-08-20，量过）

可运行性 1/27 的唯一入口是 `connections`（生成侧总数 0，基准 44）。
开工前先量了天花板：**基准 44 条里，只有 6 条（14%）能在源场景的块文本里
找到目标场景的名字。** （`tools/_diag-connections.ts`）

但那 38 条无据的**不是随机的，是三种可机械推导的结构**：

| 类型 | 条数 | 说明 |
|---|---|---|
| **返回边** | **18（41%）** | `返回镇上`、`返回特里坎家`、`从绳梯向上返回卧室`……**每条 `前往X` 都配一条 `返回`**。这是双向化规则，不需要抽取 |
| **枢纽放射** | **8** | `普瑞米尔`（镇子）一个场景 8 条出边全是 `前往X`，**有据 0 条**。作者搭的中心辐射，原文不会写「从镇上可以去警察局」 |
| 嵌套推进 | 其余 | `农场 → 农场外围 → {农场主别墅, 谷仓形建筑} → 建筑内 → {中控室, 卧室} → 下水道 → 维修间`，地理包含关系 |

前两类合计 **26 条（59%）**。

**而那 6 条有据的恰恰印证了这个判断**：`前往中控室（右侧有亮光）`、
`前往艾德里安的卧室（左侧关着门）`、`尝试进入证物室`、`前往下水道`——
**原文只在「站在这里能看见那扇门」的时候才写出去向**。看不见的地方，作者靠结构知识连。

**所以 connections 与本轮做过的一切都不同**：线索、物品、`findMethods` 都是
「文本里有，把它认出来」；连接是「文本里没有，但结构有规律」。
按前者的路子做，天花板是 14%。

**可走的方向**（都还没验）：

1. **双向化**——先抽到的每条前向边自动补一条返回边。规则可做，覆盖 41%。
   风险：基准里 `艾德里安的农场` 是单向漏斗（只有一条出边、没有回边），
   无脑双向会造出原作没有的路。
2. **枢纽识别**——「多数场景都返回它」的那个场景就是枢纽，反过来给它补全放射边。
   这是从返回边反推，与 1 互为因果，得想清楚先有谁。
3. **包含关系**——`农场外围`/`农场主别墅`/`谷仓形建筑` 都属于 `艾德里安的农场`，
   这层关系在标题层级里（`sectionize` 的块层级）可能有，还没查过。

**量它的判据也要换**：不是「抽对了几条」，而是**可达性**——从枢纽出发能走到几个场景。
内容相似度对连接没有意义：连错了地方和没连，diff 上都是一条 `missing`，
但前者能跑、后者跑不了。

> **⚠️ 上面这句「判据换成可达性」是错的，下一节量出来了：可达性能被垃圾解刷满。**
> 留着原文，因为它是提出后一小时内就被自己的测量推翻的——而当时它看起来是显然的修正。

### LLM 推连接图：F1 0.77，但模组断成两半（2026-08-20）

`connections` 已被量定为**结构推断**而非抽取。三个候选方向里：

- **包含关系出局**：场景名共享地点词的 10 组里只有 5 组真有连接（精确率 50%、召回 12%），
  而且被人名污染——「艾德里安」出现在 4 个场景名里，他是反派不是地点。
- **文档顺序**只能解释一小半（相邻 43%，链精确率 63% 但正确边可达 2/20）。
- **直接问模型**——没试过的那个，`tools/_exp-conn-infer.ts` 验了它。

给模型的只有生成侧的 27 个场景名与描述（**基准只在打分时读，绝不进 prompt**），
让它推「能从哪走到哪」，并提示枢纽/嵌套/双向这几种常见结构。

**结果：产出 40 条边，命中 32 条。F1 0.77（精确率 80% / 召回 74%）。**

| 策略 | F1 | 正确边可达 |
|---|---|---|
| 什么都不产 | 0.00 | 1 |
| 顺序双向链 | 0.59 | 2 |
| 一半对一半 | 0.51 | 12 |
| **LLM 推断** | **0.77** | **9** |
| 全连接 | 0.20 | 20 |
| 基准本身 | 1.00 | 20 |

**F1 远超所有刷法，而正确边可达只有 9/20 —— 判据第一次实用就抓到了它该抓的东西。**

43 条只缺 11 条，但缺的位置是致命的：

```
缺 普瑞米尔→艾德里安的农场
缺 与艾德里安的会面→艾德里安的农场
缺 艾德里安在镇子内的住宅→艾德里安的农场
```

**通往农场的三条路全缺了**，于是农场那半边（农场外围、农场主别墅、谷仓形建筑、
建筑内、中控室、卧室、下水道、维修间）整片断开，模组被切成两个不连通的部分。
调查员在镇上转得很顺，永远到不了案发现场。

**F1 0.77 完全看不出这件事。** 上一节特意把判据做成配对的，理由就在这里。

**失败是结构性的，不是随机的**：农场内部 6 条边**全对**（双向、嵌套枢纽都正确），
镇上那半边也对，一条错的农场入口都没编——是**压根没产**。
模型画了两张各自正确的地图，从没问过「怎么从镇上去农场」。

### 「要求连通」无效，「指出缺口」有效但太贵（2026-08-20）

顺着上一节的诊断试了两条修法。

**修法一：prompt 里直接写「整张图必须是连通的」，还提示当心区域之间的衔接。**
→ **输出一字未变**（40 条边 / 命中 32 / F1 0.77 / 可达 9）。
已确认那句话确实进了 prompt、响应是新生成的。
**模型不会因为被要求就去做全局可达性检查。** 局部结构推理好，全局约束不检。

**修法二：由我们算出不连通的分量，针对每个缺口单独追问。**
这是把「分族追问」（条目分类 67%→94% 的那招）搬过来：不笼统提要求，
而是把缺口指给它，一次问一件具体的事。分量必须用**产出的图**算——运行时没有基准。

第一次跑这个实验时两阶段的数混在一起没法归因（第一遍在 temperature 0.1 下
本身就摆动，40 条 / 42 条），所以改成**同一次运行内分阶段各打一次分**：

```
第一遍      边 42 / 命中 30 / F1 0.71 / 正确边可达 9
追问补边后  边 63 / 命中 31 / F1 0.58 / 正确边可达 17
补边 21 条，其中对的 1 条，可达净变化 +8
```

**21 条补边只有 1 条对，可达性却涨了 8。**

不矛盾——可达性只走正确边。农场内部那 6 条边本来就连对了，只是走不到；
**一条正确的衔接边把整片区域解锁了。模组能不能跑，系在单独一条边上。**

代价是精确率 71%→49%：为换 1 条对的边编了 20 条错的。

**结论**：机制对，prompt 太放任。

### 追问时「要少不要多」：错边减半，收益不减（2026-08-20）

把追问 prompt 改成明确要求克制——「只给最可能的那一条入口，至多两条，
多连会造出原作里没有的路」。

```
放任追问   补边 21 条，对 1 条，F1 0.58 / 正确边可达 17
约束追问   补边  9 条，对 1 条，F1 0.66 / 正确边可达 17
```

**可达性的收益一分没少（+8），错边少了一半以上**，精确率 49%→61%。

这次对比是干净的：两次跑的第一遍给出**完全相同**的数（42 / 30 / F1 0.71 / 可达 9），
所以差异确实来自追问方式，不是第一遍的摆动。

**但代价要说清**：补边后 F1 0.66 仍**低于**第一遍的 0.71。9 条换 1 条对的，
这是真实的取舍——**用精确率买可跑性**。

判据配对的价值正在这里：这个取舍**看得见、可决策**。
若只报 F1，补边这一步会被判为「变差了」而砍掉，而它恰恰是让模组能跑的那一步；
若只报可达性，21 条和 9 条的版本没有区别，没人会去优化 prompt。

### 口径校正：connections 里没有一条是地理问题（2026-08-20）

**前面几节都在让模型「推断场景之间的位置关系」，这个框架是错的。**
把基准 44 条边拆开看，它是三样东西，没有一样是地理：

| 类别 | 条数 | 是什么 |
|---|---|---|
| 枢纽模式 | 15（34%） | 惯例。8 条「镇上→X」+ 7 条「X→镇上」。知道谁是枢纽就能按规则生成 |
| 局部嵌套 | 22（50%） | 包含关系，11 组双向父子对（农场↔外围、谷仓↔大厅、卧室↔下水道…） |
| 线索解锁 | ~7（16%） | 「知道了 X 才能去 Y」 |

（曾一度记成「返回边 18 + 枢纽 8 = 26 条机械」，**错了**——返回边大多回的是
局部父节点，不是枢纽。真回枢纽的只有 7 条。）

**这解释了模型为什么那样失败**：它把唯一真该推断的那类（嵌套）做对了 ——
农场内部 6 条边全对，双向、层级都正确。漏掉的全是枢纽模式与线索解锁，
**而那两类根本不在文本里，也不是地理，是惯例和线索链**。
拿地理去问，问不出惯例。

**线索解锁那类，类型系统里本来就有对应物**：`SceneConnection.requiredClueId`
（`src/module/types.ts:310`），手写基准一处没用（全 44 条无门禁）。
原文的「根据身份证上的地址，调查员可以找到这个地方」，
更准确的建模是**一条带 `requiredClueId` 的边**，而不是一条路。

**方向改为**：不要再让模型推地理。分三条各按各的来 ——
枢纽按规则生成（只需先认出枢纽）、嵌套继续交给模型（它已经做得好）、
线索解锁走 `requiredClueId`。前面那些「补边」实验是在用一种手段打三种问题。

### 口径校正：场景「精确率 20/27」是个误导性说法（2026-08-20）

一直把块分类的成绩记成「命中 20 / 误报 7 / 漏报 0」，并据此说
「场景精确率 20/27，得去提精确率」。**这个框架是错的。**

`src/ingest/classify-sections.ts:13` 的分类体系只有 4 个格子：
`scene` / `npc` / `structure` / `rule`。
**没有物品、线索、文件、事件的位置。**

那 7 个「误报」在这个体系里**没有正确答案**：

| 块 | 它其实是 |
|---|---|
| 奇怪的卡片 | 物品 / 线索 |
| 绑架犯的报道 | 线索文件（handout） |
| 艾米丽与爱莉的棺材 | 场景内的发现物 |
| 关于艾米丽难产的事件 | 背景事件 |
| 在小镇内询问路人 | 行动 / 流程 |
| **比较大的奇怪管道** | **一条连接** |

模型只能在 4 个里挑个最不离谱的，而「有描述的实体」最像 scene。
**这不是分类判错，是体系里缺格子。** 同一份记录里**漏报 0** ——
真场景一个不落，召回是满的，所谓「精确率不够」全部来自无处安放的条目。

**最讽刺的一条**：`比较大的奇怪管道` 在基准里根本不是场景，是一条连接 ——
`src/module/barn-of-premier.ts:813` 的
`{ targetSceneId: "sewer", condition: "通过奇怪管道（下水道深处）" }`。
花了好几轮想把 connections 推出来，其中一条一直躺在被当作「场景误报」的块里。

**所以下一步不是「提精确率」，是给分类体系加格子。**

### 加一个 item 类：误报 7 → 4，其余全部持平（2026-08-20）

`SectionKind` 加 `item` 一类，prompt 里给出判别界线
——「看调查员是**走进去**还是**拿起来**」。只加一类没有一次加四类，
是为了能归因。

```
场景   身份覆盖 20/20（不变）   真漏报 0（不变）   真误报 7 → 4
物品   覆盖 9/10、精确率 9/19（不变，无倒退）
评分键 左手边 39/39 完全一致（不变）
```

移出场景表的正是预测的那三个：`奇怪的卡片`、`绑架犯的报道`、`艾米丽与爱莉的棺材`。

item 块不会被无声丢弃：`buildScenes` 现在会报
`3 个块判为 item（是物品/线索，不是地点），本轮无人消费`。
它跟 npc/structure/rule 的「跳过」不是一回事 —— 那三类本来就不该变成任何东西，
而 item 块是**认出来了却还没人接**。实跑 report 里已确认这条会打出来。

**有意为之的一处**：item 块**不进** `toItemInputs`。
那里给每个条目挂的 `sceneId` 取自 `ids[i]`，而非 scene 块的那个 id
从来没被写进任何 `Scene.id` —— 让 item 块进去只会造出一批
指向不存在场景的悬空引用。物品块怎么落地是下一轮的事。
（这也是为什么物品那三个数纹丝不动。）

**剩下 4 个误报，性质不同了**：
`在小镇内询问路人`（行动流程）、`关于艾米丽难产的事件`（背景事件）、
`比较大的奇怪管道`（其实是一条连接）—— 这三个仍是缺格子。
但 **`旅店` 是个真地方**，只是基准没把它建成场景 ——
**那不是体系问题，是基准的取舍**，再加格子也解决不了。
所以「误报清零」不是一个能达到的目标，4 里至少有 1 个是口径差异。

### 层级路线：层级判断 9/11，但规则会把垃圾连上枢纽（2026-08-20）

换个问法：不问「能从哪走到哪」，**只问「谁在谁里面」**，边由两条规则机械导出
（子↔父，顶层↔枢纽）。`tools/_exp-conn-hierarchy.ts`

```
层级路线（滤掉上游场景误报）  边 38 / 命中 33 / F1 0.81 / 精确率 87% / 可达 13
直接推边（未滤）              边 44 / 命中 36 / F1 0.83 / 精确率 82% / 可达 11
```

⚠️ **这两个数不能直接比** —— 一个滤过一个没滤。要公平得把两边的边集都存下来同样处理，
当时没存直接推边那次的边集。**别拿这两个数下结论**，下一轮补齐再说。

不受这个影响、可以确定的两件事：

**一、层级判断本身很准：11 组嵌套对里对了 9 组。**
错的 2 处是同一类：`农场主别墅`、`谷仓形建筑` 挂到了 `艾德里安的农场` 而非 `农场外围`
—— **差一层**，而且语义上说得通（别墅确实在农场里），只是基准经外围中转。

**二、52 条边里有 14 条是我的规则造成的，不是模型的错。**
模型**正确地**给 `奇怪的卡片`、`绑架犯的报道`、`关于艾米丽难产的事件` 这些
上游误报条目判了 null 父节点。是「顶层一律连枢纽」这条规则硬把它们连了上去，
每个两条边。而直接推边那次没这个问题 —— 问「怎么走」时模型自己就不往非地点连。

**教训**：机械规则会**放大上游的误报**。场景抽取的精确率是 20/27，
这 7 个误报在推边时基本无害，一进规则就变成 14 条错边。
规则省了推断，但也丢掉了模型自带的常识过滤。

### 枢纽：确定性信号全废，问模型 5/5（2026-08-20）

上一节把 connections 拆成三类后，枢纽模式那 15 条（34%）只要认出枢纽就能按规则生成。
所以先量枢纽认不认得出来。`tools/_diag-hub.ts`

**四个确定性信号全无区分度**（真枢纽是「普瑞米尔」）：

| 信号 | 真枢纽排名 | 值 |
|---|---|---|
| 被别的场景提到的次数 | 2 / 27 | 1（另有 8 个也是 1，证物室还是 2） |
| 提到别的场景的个数 | 4 / 27 | 1 |
| 文档位置 | 4 / 27 | — |
| 描述长度 | 8 / 27 | — |

数值全是 0/1/2。**场景之间在文本里几乎不互相提及** ——
这跟「44 条边只有 6 条有文本依据」是同一件事的另一面。

**问模型：跑 5 次，5 次全答「普瑞米尔」。**

这符合这条线上反复出现的规律：**惯例知识问模型，文本事实靠抽取**。
枢纽是前者，所以确定性信号找不到它，而模型一次不错。

**但有个前提还没解决**：知道枢纽之后，要连的是「所有**顶层**场景」，
不是所有场景 —— 基准里枢纽只有 8 条出边，中控室、下水道这些嵌套深处
并不直连镇子。**判断谁是顶层，仍然要靠嵌套关系**。
所以枢纽这一步不能单独用，得跟嵌套那一步配起来：
先定层级，顶层的连枢纽，非顶层的连各自父节点。

### 描述给多少字，与补边其实是在赌一条边（2026-08-20）

**上一节「机制对、只是 prompt 太放任」是过度归纳，这里更正。**

**（一）描述截断是自找的损失。** 给模型的描述原本截到 90 字，这个数是随手定的、没依据。
查原文发现关键信息常在 90 字之后——农场的「再稍微往里有两个比较显眼的建筑。
一间刷着红油漆的类似谷仓的建筑，和一个农场主别墅」正是包含关系。
做成 `CONN_DESC_CHARS` 可调后测三档，看第一遍（补边前）：

| 描述字数 | 边 | 命中 | F1 | 正确边可达 |
|---|---|---|---|---|
| 90 | 42 | 30 | 0.71 | 9 |
| 400 | 46 | 34 | 0.76 | 10 |
| 全文 | 44 | 36 | **0.83** | 11 |

**文本越多边越准，单调**（召回 72%→81%→84%）。

**但可达性纹丝不动（9→10→11）。** 这反过来证实了：
跨区域那道缺口**确实不在文本里**，不是被我截掉的。两件事各归各——
截断伤的是精确率与召回，断开是原文的性质。

**（二）补边是在赌一条边。** 三次跑的可达净变化是 **+8、+9、+0**；
最后这次 13 条补边**一条都不对**。

原因清楚：农场内部 6 条边本来就连对了，差的只是**入口那一条**。
猜中就解锁整片（+8），猜不中就白加十几条错边（+0）。
**全部收益押在单独一条边上。** 三次中了两次，n=3，说不出成功率。

所以补边**不是一个可靠的机制**，是一次高方差的赌。要下结论得重复跑，
而不是从三次里挑最好看的那次报出来。

**目前的数（都不算定论）**：第一遍全文 F1 0.83 / 可达 11 是边质量最好的；
400 字加补边 F1 0.72 / 可达 19 是可达性最好的。哪个更该要，取决于
管线是要「准但可能断」还是「通但掺错边」——这个取舍还没定。

起点是 F1 0.00 / 可达 1。

⚠️ **这是实验脚本的成绩，不是管线的成绩。** 读取层至今一条边都不产 ——
`src/ingest/build-scenes.ts:95` 硬写 `connections: []`，推图只活在
`tools/_exp-conn-infer.ts` 里，从没接进 `build-scenes`。
端到端跑出来的 `ModuleData` 里 connections 仍然是 0。
要把它变成管线的成绩得改行为，开分支走评审。

**顺带查清了一件相关的事**：断开**不是**线索门禁造成的。
门禁机制是有的（`src/module/types.ts:310-312` 的 `requiredClueId` / `checkRequired`，
运行层在 `src/world/module-loader.ts:60` 据此置 `locked`），
但手写基准 `src/module/barn-of-premier.ts` 里这两个字段**用了 0 处**——
44 条边全部无门禁，`condition` 只是给人看的描述文字。
所以「算可达性时无视条件」这个口径是对的，不存在虚高。
（若将来读取层开始产 `requiredClueId`，判据得跟着改。）

**还没验的**：两段式——先让模型给场景的从属层级，再由层级机械导出边。
以及缺口追问目前是每个分量问一次（这次 5 次调用），能不能合并成一次。

### connections 的判据：F1 + 正确边可达，且先攻过再采用（2026-08-20）

前两个判据（diff 差异数、可达性）都是**提出之后才被自己的测量证伪的**，各浪费一轮方向。
所以这次反过来：先定候选，**拿刷法攻它**，攻不动才用。`tools/_diag-conn-metric.ts`

**判据是配对的，不是单数：**

- **边集 F1** —— 挡「乱刷全连接」与「什么都不产」
- **正确边可达** —— 只留在基准里存在的边，再算从起点能走到几个场景。挡「边对但集中在孤立角落」

**五种刷法的攻击结果：**

| 策略 | 产出 | 命中 | 精确率 | 召回 | F1 | 正确边可达 | 裸可达 |
|---|---|---|---|---|---|---|---|
| 什么都不产（当前状态） | 0 | 0 | 0% | 0% | 0.00 | 1/20 | 1/20 |
| 全连接（刷召回） | 380 | 43 | 11% | 100% | **0.20** | 20/20 | 20/20 |
| 顺序双向链（刷可达） | 38 | 24 | 63% | 56% | 0.59 | **2/20** | 20/20 |
| 只产 6 条正确（保守） | 6 | 6 | 100% | 14% | 0.24 | 5/20 | 5/20 |
| 一半对一半瞎连 | 44 | 22 | 50% | 51% | 0.51 | 12/20 | 20/20 |
| 基准本身（上限） | 43 | 43 | 100% | 100% | 1.00 | 20/20 | 20/20 |

**没有一种刷法能同时骗过两项。** 全连接把正确边可达刷满（所有基准边都被包含）但 F1 只有 0.20；
顺序链把裸可达刷满但正确边可达只有 2/20。

**两个数排序相反，所以谁也替代不了谁**：顺序链 F1 0.59 > 一半对一半 0.51，
而正确边可达 2/20 ≪ 12/20。F1 高的那个反而更走不通。

**顺带一个意外**：顺序双向链的精确率有 **63%** —— 比预想高得多，
说明场景的文档顺序在不少地方确实跟着模组流程走。但它对的边是散的、连不成路，
这正是「对但走不通」那一类，单看 F1 看不出来。

**采用**：以后报 connections 一律同时报这两个数，不单报任何一个。
当前状态是 `F1 0.00 / 正确边可达 1/20`。

### 可达性也会骗人：朴素解 43/43 而精确率 21%（2026-08-20）

`tools/_diag-conn-order.ts` 量了「文档顺序能不能预测连接」，顺带把上面那个判据证伪了。

**基准连接的文档顺序跨度**（目标块序号 − 源块序号）：

```
  -12 █1   -11 █1   -8 █1   -5 ██2   -3 ██2   -2 ███3   -1 ██████████10
    1 █████████9    2 ████4    3 ██2    4 ██2    5 ██2
    8 █1    10 █1   11 █1   12 █1   16 █1
```

**相邻（±1）占 19/44（43%）**，但长尾拖到 ±16。所以「相邻」能解释一小半，
剩下一半是跨越式的枢纽边与回边，**顺序完全预测不了**。

**朴素规则**（相邻块之间连双向边）：产出 84 条、命中 18 条 → **精确率 21% / 召回 42%**。
**而可达性 43/43 —— 全通。**

**这就是判据被刷满的样子**：一条把所有块按排版顺序串起来的链，可达性满分，
而 79% 的边是错的。调查员确实走得动，只是走到的地方与模组的地理毫无关系。

**所以连接必须同时看两个数，任何一个单独看都骗人：**

| 只看这个 | 会被什么骗 |
|---|---|
| diff 差异数 | 描述抄得像就以为接近能跑（见 §可运行性是 1/27） |
| 可达性 | 一条乱串的链就满分（本节） |

**一个测量瑕疵要标出来**：这个朴素规则跑在 **43 个块**上，而其中只有 27 个被判成场景。
`43/43` 是块级可达性、不是场景级，脚本没先按分类结果过滤，**这个数偏乐观**。
下次量要先过滤。

### ⚠️ 一直在报的那个数不衡量目标：可运行性是 1/27（2026-08-20）

到目前为止所有指标都是**内容相似度**——「生成的 `ModuleData` 离基准有多远」。
`差异 179 处` 听起来像挺接近了。但从来没有人问过另一个问题：**引擎能不能跑它。**

`tools/_diag-runnable.ts` 量了：

| | 生成侧 | 基准 |
|---|---|---|
| 场景数 | 27 | 20 |
| **从第一个场景出发可达** | **1** | **20** |
| `connections` 总数 | **0** | 44 |

跑一局必须有的东西，生成侧有几样：

| | |
|---|---|
| 场景之间有连接 | **无** —— 调查员哪儿也去不了 |
| 场景里有线索 | **无** —— 调查无事可做 |
| 场景里有 NPC | **无** —— 没人可对话 |
| `npcs` / `endings` / `prologue` | **无** —— 根本没产出这些数组 |
| `items` | 有（本轮刚做出来） |

**两个口径别混**：内容相似度在涨，不代表可运行性在涨。
场景描述抄得再准，`connections` 空着就是走不动。
本轮把物品覆盖从 0 做到 9/10、把条目分类从 22/33 做到 31/33，
**可运行性一格没动**——因为这两项都不产出连接。

⚠️ 这里的 31/33 一度**只是实验脚本的成绩**（2026-08-20 补注）：
`_run-ingest.ts` 里一处 followup 都没有，实跑 report 长期报 22/33（67%），
而文档把它跟「物品覆盖 9/10」这个管线真数并列着写，读起来像都到手了。
**现已接进管线**（见「接进管线」一节），report 报 31/33。
但那条教训留着：**这条线上「实验成绩」与「管线成绩」会分叉，看数先问是哪一种。**
connections 那边一度也是分叉状态（F1 是脚本成绩、管线产 0 条边），
**2026-08-20 已接进管线**，实跑 48 条边、裸可达 24/24。

### 接进管线：分族追问上线，顺带把物品精确率带上去（2026-08-20）

修法验证成功不等于生效。分族追问验成 31/33 之后一直躺在 `_exp-clue-followup.ts` 里，
管线跑的还是一次性六选一。这次把它接进去。

逻辑落在 `src/ingest/classify-followup.ts`（**进版本库**，
以前 prompt 只存在于 gitignore 掉的 `tools/` 里）：

```
条目分类准确率   22/33（67%） → 31/33（94%）
物品精确率        9/19（47%） →  9/11（82%）   ← 没预料到的收益
物品覆盖          9/10（不变）
```

### 把编排提进 src：管线终于有了进版本库的入口（2026-08-20）

### ⛔ 决定性事实：场景进入时线索就被跑光了（2026-08-20，已被上面那条取代）

  前半永远为假，后半接住了，**行为正确**，只是句死代码。
- TS2339 那个**是真 bug**。`secondPlayer` 不存在 → `p2` 恒为 `undefined` →
  **队友的 HP 一次都没显示过**，而那个脚本抬头就写着「洛水 + 希尔妲」。
  队友实际在 `state.companions` 里。改成按名字取而不是按下标 —— 下标会随创建顺序变。

**这就是这条改动的全部理由**：一个「显示两个玩家」的脚本，
有一半从来没显示过，而它安静地跑了不知道多久。
本轮重构 runner 时两次改出未定义变量、typecheck 两次全绿，是同一个洞的另一种表现。

2. **边界测试是全文扫字符串的，注释里提到那个模块名就会被自己判红。**
   `pipeline.ts` 的注释原本写着「见 ...-boundary.test.ts」，那串字里含着被禁的子串。
   处理方式是**改注释，不是放宽测试** —— 为了让自家注释过关去钝化一道安全网，方向就反了。
   （同一类事这一天栽了两次，另一次是「不许出现 readFileSync」的测试
   被解释这条规则的注释本身判红。）

**还有一条结构性的**：`ModuleSupport` 里 `evaluateEnding` 是个函数、
`bossNpcIdPattern` 是个 RegExp，JSON 序列化不了，**读取层永远给不了**
（spec 里已记为硬边界）。所以「读取层产出可运行模组」不是读取层单方面能完成的事，
需要运行层那边配合出一个「支持配置由人写、数据由读取层产」的分工。

**这条该怎么用**：不是说内容相似度白做了——线索/物品/连接总得先抽出来才谈得上连通。
但**报告里应该同时印这两个数**，否则「差异从 179 降到 150」会被读成「接近能跑了」，
而那可能只是描述更像了、连一条路都还没有。

### 行归属做对了，可分类没涨——判据选错了（2026-08-20）

上一节推断「剩下 2 个分类错误都是根因 B（同页续句）的下游」，并据此预测：
把续句接回条目，分类应当 31/33 → 33/33。`tools/_exp-line-attribution.ts` 验了这个预测。

**行归属本身做得相当好。** 21 个候选行交给 LLM 判「还属于上面那个条目，还是回到场景叙述」，
逐行看判得对：

```
[接回] p5:L16  此时的他处于一种疯狂的边缘。成功的社交类技能才可以让他冷静下来。   ← 正是那句枢纽
[接回] p8:L7   这是一份有些年份的文书，上面记录了一项购买…                     ← 正是 p8:L6 缺的正文
[接回] p9:L14  如果伤害大于调查员耐久最大值的一半，则有截肢的风险。             ← maimAtHpRatio 的出处
[留下] p3:L10  特里坎夫人还有一个小女儿，年仅 5 岁。                           ← 场景级，正确留下
[留下] p7:L2   导航失败的情况，调查员可以寻求本地 NPC 的帮助…                  ← 场景级 KP 提示
[留下] p8:L8   在城镇中的可选事件                                             ← 被截断的标题
```

**但分类 31/33 → 30/33（净 −1）。** 预测错了：

- `p5:L15` **拿到枢纽句之后仍判 `event`**
- `p8:L6` **拿到正文之后仍判 `item`**
- `p11:L9`（中控台的开关）**本来是对的，现在错了** —— 批内耦合，13 个条目的正文变了、
  整个 prompt 就变了（见 §分类器的逐条输出不是独立的）

**真实原因是基准自己的取舍边界，不是文本缺失。** `转购协议` 按「容器 vs 内容」那条轴
就是 `thing`（一份可以拿走的文件），而基准把它收成 `Clue`；
而同样是文件的 `老旧文件`，基准**同时**收成 `Clue` 与 `ModuleItem`。
基准对文件类本就不一致，这不是补文本能解决的。

**更要紧的教训是判据选错了。** 行归属真正改善的是**文本完整度**——
陷阱机制、`findMethods` 召回、描述保真；而条目分类早就因为别的原因接近天花板了。
拿分类当行归属的判据，等于用一把量不到的尺子。

**下次量行归属该用的判据**（都还没做）：`maimAtHpRatio` / `firstAid` 这类
「机制写在续句里」的字段能不能被 `extract-trap` 抽到（注意它现在**没有** `maimAtHpRatio`
的抽取规则，得先加）；条目正文与基准 `Clue.description` 的重合度；
以及 `findMethods` 的技能召回。

**顺带修掉一个测量事故**：这个实验第一版把两个追问 prompt 重打了一遍简写版（删掉了例子），
于是同一条管线的基线从已确立的 31/33 变成 29/33。**prompt 的字面内容是测量条件的一部分**，
两处各写一份等于两台不同的秤。已抽成 `tools/_followup-prompts.ts` 只此一份。

### 条目分类的真实准确率：22/33，而 11 个错误全指向同一个方向（2026-08-20）

评分键（`src/ingest/scoring-key.ts`）落地之后，`tools/_run-ingest.ts` 每次实跑都会算这一项。
**在有键之前算不出来**——只能拿「生成物品的名字对不对得上基准」间接推，而那条路只覆盖 43%。

**22/33（67%）**。另有 4 条不计分（键说 `none`，基准没收，无所谓对错）：
`搜查一层`、`搜查二层`、`受害者床位边上`、`下水道深处的房间`。

| 预测 | 实际 |
|---|---|
| `clue` 8 | **clue 8** ✓ |
| `connection` 3 | **connection 3** ✓ |
| `trap` 4 | **trap 4** ✓ |
| `event` 4 | clue 3 / event 1 |
| `item` 14 | clue 8 / item 6 |

**11 个错误全是同一个方向：某某 → 实际是 `clue`。** 分类器**从不把别的东西误判成线索**。
所以问题是召回不是精确率：

- `clue` 精确率 **8/8 = 100%**，召回 **8/19 = 42%**
- `connection` 与 `trap` 各 100%，两项都可以直接信

判错的 11 条分两族，族内高度同形：

**族一 · 判成 `item`（8 条）—— 全是「容器家具 / 搜查动作」**
`枪械柜`、`床头柜`、`在一旁的冰箱与储物柜`、`中控台的开关`、
`侦查休息区/宣言仔细检查床底`、`侦查卫生间/…`、`侦查餐厅/…`、`抽屉里的…转购协议`

**族二 · 判成 `event`（3 条）—— 全是「条件叙述，但它就是那条线索」**
`如果调查员投掷了成功的精神分析…`（= `clue_adrian_psychoanalysis`）、
`如果他冷静了下来，会认罪…`（= 同上 + `clue_adrian_farm_location`）、
`母女的缸中脑`（= `clue_final_brain_jars`）

**单方向错误比散布错误好修得多**，而且这里还有一条硬约束：
**prompt 里已经拿 `床头柜` 当「这是线索」的范例，模型仍把它判成 `item`。**
所以「再多写点说明」大概率无效，得换手段。可考虑的方向（都没量）：
把「是不是可拿走的实体」与「是不是一条信息」拆成两个独立判断（两族错都能覆盖）；
或允许多标签（基准里 `老旧文件` 本就同时是两者）；或逐条问而不是整批问
（整批问会让一条的文本变化翻掉另一条的标签，见 §分类器的逐条输出不是独立的）。

`tools/_diag-confusion.ts` 拿上一次实跑的 37 条分类结果，逐条去基准里找它对应什么结构。

**算一下上限**：32 − 4(a) − 1(b) − 5(c) − 1(d) = **21**，正好等于键当前引用的 21 条。
这不是巧合：键覆盖的就是「按条目能够到的全部」。所以

把 (c) 那五行捡回来能把上限抬到 26；捡法与根因 B 是同一件事
（`▶` 之后到下一个 `▶`/标题之间的行归谁），**归 LLM 那一层**。

> `clue_final_coffin` 对，`黑色钱包` 错——上面那张六行表里没有它，全书也搜不到 `▶黑色钱包`。

**键的左手边现在也有人看了。** 单测只验键名形态（`/^p\d+:L\d+$/`），`"p99:L99"` 照样过；
而键自己的文件头就写着行号是**清洗后**的、「清洗逻辑一变行号就漂」。漂一行那条就永远配不上，
不报错不报红，只是从此不参与计分。这个检查需要 PDF（在仓库之外），所以**同 `pdf-source` 的内容保真一样
归实跑器报，不进单测**：`_run-ingest.ts` 现在断言「抽出的 `sourceKey` 集合 == 键名集合」并**印两个方向的差**
（只印一侧的话，「漂了一行」看起来就只是「少了一条」，看不出是同一条挪了位置）。
当前实跑：`抽出条目 39 / 键 39 —— 完全一致`。

### 线索轮的依赖顺序：findMethods 不能先做（2026-08-20，量过）

开线索轮时的直觉是先做 `findMethods`——技能名与难度词是死板形态、与 `extract-trap` 同一类，
而且**基准里的技能名逐字来自原文**（16 条 `type=skill` 里 15 条的 `skillName` 就写在
它自己的 description 里），所以「每个场景的技能多重集」看起来是个可对齐、不需要人工评分键的口径。
量完之后这条路被否了，理由不是口径不好，是**它的上游还没就位**。

**先量的第一件事：基准的 `type` 自身不一致。** 3 条 `observation` 的 description 里写着 `侦查`
（`侦查或挪开床头柜`、`声明仔细检查路周围物品或者一个成功的侦查`、`侦查餐厅/宣言仔细检查餐桌`），
而另外 3 条同样是侦查的标成 `skill`。**所以别拿 `type` 计分**——那是拿一个自身有噪的标签计分。
技能名多重集不受这个影响。另有 1 处基准写 `话术` 而原文写「通过**社交**技能」，是手写替换，
抽不到——上限 18/19 不是 19/19。

**第二件：原文技能词比基准记录的多 2.8×**（54 处 vs 19 处，`tools/_diag-skillwords.ts`）。
超产的 33 处集中在七个「基准记 0」的场景，而它们记 0 不是遗漏——**那些技能属于别的结构**：
`农场外围` 那 12 处是陷阱区的 `幸运/侦查` 探查与捕兽夹的 `力量` 挣脱（→ `TrapMechanics`）；
`谷仓形建筑` 那 7 处是 `攀爬/跳跃/锁匠/力量` **进入方式**（→ `SceneConnection.checkRequired`）；
`农场主别墅` 的 `急救/闪避` 属硫酸陷阱。
**技能词好抽，难的是判断每一处属于哪个结构**——又是「六种东西里的哪一种」那个问题。

**第三件，决定性的：限定「已判为 `clue` 的条目」之后，超产 2.8× 变成产不足 0.6×**
（12 处 vs 19 处，`tools/_diag-skill-scoped.ts`）。精确率上去了，召回塌了，而塌在哪很说明问题：

| 场景 | 基准 | 只 clue | 塌陷原因 |
|---|---|---|---|
| 加比的拖车房 | 3（侦查×3） | 0 | 三个条目**就是**基准那三条线索，却被判成 `item` |
| 交火现场 | 2 | 0 | 同上 |
| 艾德里安的卧室 | 2 | 0 | 同上 |
| 与艾德里安的会面 | 2 | 0 | 被判成 `event` |
| 报亭 / 霍姆斯医院 / 警察局 | 4 | 0 | **一个 `▶` 都没有**，技能写在块正文里 |

前四行是**分类器的错误在往下传**——正是上面记的那个系统性误报（物品/线索边界）。
后一行是条目级抽取的硬天花板。

**结论（依赖顺序）：**

1. **先修物品/线索边界。** `findMethods` 的抽取质量被它上界，先做 findMethods 等于在错分类上
   建指标。而修它大概率不是改 prompt 文字——prompt 里已经拿 `床头柜` 当「这是线索」的范例，
   模型仍判成 item。
2. **findMethods 抽取必须能读块正文，不能只读条目**，否则 `报亭`/`霍姆斯医院`/`警察局`
   永远为 0。而读正文就要面对根因 B（同页续句归属）。
3. 计分用**技能名多重集**，不用 `type`；上限 18/19。

### `▶` 不是线索标记（2026-08-19）

上一轮把 39 个 `▶` 条目整批丢弃，理由写的是「属线索/物品，留给下一轮」。
这轮逐条对回基准，那句话说得太粗——`▶` 底下混着六种东西：

| `▶` 条目 | 在基准里其实是 |
|---|---|
| `捕兽夹` / `锯短霰弹枪拌锁陷阱` / `音响陷阱` / `硫酸陷阱` | `ModuleItem.trap` |
| `防盗门的钥匙` / `农场的照片` / `驾驶证` / `住宅钥匙` / `老旧文件` | `ModuleItem` |
| `侧面的防盗门` / `一旁的杂物堆` / `拉门` | `SceneConnection`——进入方式，不是线索 |
| 菲碧·特里坎名下 2 条 | `ModuleNPC.knowledge` 与 `.secrets` |
| 与艾德里安会面的 3 条 | 分支结局叙事 |
| `侦查休息区/宣言仔细检查床底` 等 | 才是 `Clue` |

**先做物品不做线索，是因为只有物品能按名字计分**：基准 10 个 `ModuleItem` 里 9 个的
`name` 能在 `▶` 名字里原样找到，缺的是 `黑色钱包`，所以**上限就是 9 不是 10**。
先前这里只写「PDF 里没有对应条目」，那句话对但没说出原因，而原因是可查的：
**原文把钱包的「内容」写成了条目，没写容器本身**——`交火现场` 全块只有两个 `▶`，
`▶驾驶证` 与 `▶住宅钥匙`，而基准 `clue_shootout_wallet` 的 description 正是
「翻看钱包可以获取：驾驶证…、住宅钥匙…」。全书 45 个行首 `▶` 里**没有任何一行是 `▶黑色钱包`**
（逐行核过，见下面 §评分键的覆盖分析 的表），所以它既不是被清洗吃掉的，也不是被判成了标题。
而 32 条线索的 `name` 是重写过的——`床头柜` → `日记本与老旧文件`，
`中控台的开关` → `中控台拉杆`——39 个条目里只有 2 个逐字命中。没有可对齐的名字就没有分数。

**三处结构性错位**，说明「一个 `▶` 对一条线索」根本不成立：`证物室` 有 3 个 `▶` 却 0 条线索
（三个全是物品，而名叫「证物室」的线索挂在 `警察局` 名下）；`维修间` 只有 1 个 `▶` 却有 4 条线索；
`报亭`、`霍姆斯医院`、`警察局` 一个 `▶` 都没有，它们的线索写在正文里。

**分类不是互斥的**：`老旧文件` 在基准里同时是 `ModuleItem old_document` 与
`Clue clue_bedroom_old_doc`。39 条里只此一例，所以本轮用单标签——但下一轮做线索时
**不能假设「已判为 item ⇒ 不是 clue」**，那种假设正是会静默丢东西的那一类。

**引用字段与内容分开算**：`ModuleItem.sceneId` 指向场景 id，生成侧是 `scene_NN`、
基准是手写意译，按名字配上后会全部报成 `changed`。这不是生成器不准，是
「id 是内部句柄」往下再走一层。`diffValues` 新增 `refFields`，这类差异单列成
`ref-mismatch`（实跑 9 处），不进 `changed`。
**注意它只拦对象的键**：`connections[].targetSceneId` 管得住，
而 `npcIds[]` 这种「引用本身就是数组元素」的形态管不住——那条路走 `walkArray`、
退回按下标比两个标量，键名在那儿不存在。做 NPC 那一轮要在数组侧另做一套。

### 根因：条目正文丢后半截，是两个原因而不是一个（待修）

> **先纠正一个错诊断。** 这一节原先写的是「PDF 读取顺序把整行甩出了条目」。
> 逐层取证之后确认**读取顺序完全正确**，问题在别处，而且是**两个互不相干的原因**。
> 取证脚本留在 `tools/_diag-strand.ts`，产物 `tools/ingest-out/diag-strand.txt`，
> 它在 `extractPages` / `cleanPageText` / `sectionize` 三个边界上各打一份，重跑即可复现。

**根因 A —— `cleanPageText` 的作用域是单页，而句子会跨页。**

`证物室` 的 `▶防盗门的钥匙` 生成侧截断成「…这种先进防盗门可」，基准是「…这种先进防盗门可不多见。」。
取证显示：**第 6 页原始文本的最后一行就是那个 `▶` 行**，页面在「防盗门可」处结束，
「不多见。」是第 7 页的第一行。而 `raw.map(cleanPageText)` 是**逐页**调用的，
行连接只在页内做，页边界上的续行接不回来。随后 `sectionize` 逐页逐行走，
第 7 页首行既不是 `▶` 也不是标题，于是归 `bodyLines` —— 而 `cur` 还停在 `证物室`
（跨页接续是 `sectionize` 有意设计的，见其文件头）。

**根因 B —— `sectionize` 的条目只吃 `▶` 所在的那一行。**

第 9 页原始第 44 行是「…捕兽夹会造成额外的 1d3 伤害。」，以句号收尾，
`cleanPageText` 判为句子结束、不与下一行连接 —— **这是它的既定行为，不是 bug**。
第 45–46 行于是自己接成「如果伤害大于调查员耐久最大值的一半，则有截肢的风险。」。
原文作者在这个条目里写了**两句**，第二句成了独立行，而条目只取第一行，
所以条目正文天然缺后半截。同一形态还有 `▶锯短霰弹枪拌锁陷阱` 的
「并且因为枪管太短，射出的弹丸往往也无法全部命中。」。

**这才是 `maimAtHpRatio` 没抽到的真原因，不是抽取器弱。** 而且这个区别很要紧：
它不是「机制写在场景正文里」（那需要跨场景推理），而是「机制写在条目的第二句、
被切成了独立行」—— 只需把 `▶` 之后、下一个 `▶` 或标题之前的行并回该条目即可。

> **根因 A 已修（`joinPages`，见 `clean-text.ts`）。** 下面这一节保留是因为它记着 B 为什么不能用规则做，
> 以及那两个诊断脚本怎么用。A 修完的实测效果与一个意外发现记在本节末尾。

**修法：A 能用规则，B 不能。这一条是量出来的，不是估的。**

「条目吃到下一个 `▶`/标题为止」这条贪心规则复现了一遍（`tools/_diag-absorb.ts`，
产物 `tools/ingest-out/diag-absorb.txt`）：39 个条目里 19 个会吸收后续行，共 25 行，
**其中跨页 4 行、同页 21 行**。

| | 行数 | 性质 | 规则能否判 |
|---|---|---|---|
| 根因 A · 跨页续行 | **4** | 上一页末行没有终止标点，纯排版换行 | **能**——`cleanPageText` 页内已经在做这件事，只是看不到跨页 |
| 根因 B · 同页续句 | **21** | 约一半是条目续句，一半已回到场景叙述 | **不能** |

同页那 21 行里，是续句的有 `如果伤害大于调查员耐久最大值的一半，则有截肢的风险。`、
`并且因为枪管太短…`、硫酸陷阱的 `必须使用清水进行急救…清水清理后不会继续伤害`、
`SC1d3+1/1d6+1。`、`1911 手枪：故障值 90…`；已经回到场景叙述的有
`特里坎夫人还有一个小女儿，年仅 5 岁。`、`导航失败的情况，调查员可以寻求本地 NPC 的帮助`、
`继续在周边搜索的话，可以应用临时武器规则`、音响陷阱之后的
`如果调查员声明以一字队伍前进…通过陷阱区需要 3 次鉴定`、`前往通道，可以看到通向两个房间…`。

两边都有以「如果」开头的（`如果伤害大于…` 属条目，`如果调查员声明…` 属场景），
所以**连词/句式这类形态判据分不开它们**。这与「这一块是不是场景」（引文启发式 15/6/5）
和「这个 `▶` 是什么」是同一类问题——**归 LLM 那一层**。

> **一条被推翻的判据。** 这一节先前写过「B 更小、收益更直接，改完 `maimAtHpRatio` 与
> `firstAid` 两处应当消失」。量完发现两件事都不对：B 比 A 大（21 行 vs 4 行）且不能用规则做；
> 而那两处的出处**全在同页**，所以修 A 不会让它们消失。别照那句话去验收。

**下一轮的顺序建议**：先做 A——4 行、形态可判、收益确定（`item_12` 的
「…这种先进防盗门可」截断就在里面），且改动局限在页边界的续接判断上。
`shouldJoin(prev, next)` 这个判据 `clean-text.ts` 里已经有了，A 要的就是在页边界上再调它一次，
别重写一份。B 留到做线索那一轮一并处理：那时本来就要对条目正文调 LLM，
「这一行还属不属于上面那个条目」正好是同一次调用能顺带回答的判断。

#### A 修完之后（`joinPages`）

现在接 **5 处**页边界（p4→p5、p5→p6、p6→p7、p10→p11、p17→p18）。
**两个分母都要写出来**：其中 **4 处**的上一行是 `▶` 条目，`_diag-absorb` 报的「跨页 4 行」
数的就是这 4 处（它只管跟在 `▶` 后面的续行）；第 5 处（p17→p18）是附录里的普通正文，
`joinPages` 连普通正文的跨页也接。这不是矛盾，但只写小的那个分母会害人——
见下面那条实际发生的缺陷。

> **第一版接了 6 处，其中 1 处是错的（已修）。** 多出来的是 **p1→p2**：它把 p2 的首行
> `事件真相（想跑的人请不要继续往下看了。）：`——一个章节标签——焊到了 p1 末尾，
> 变成「…固话号码和一行联系地址....事件真相（想跑的人请不要继续往下看了。）：」。
> 两道该拦住它的闸门同时失效：`SENTENCE_END` 里有 Unicode 的 `…`(U+2026) 但没有 ASCII 的 `.`，
> 所以 p1 末行的 `....` 不算句末；`▶`/标签那道闸门确实认出了冒号，但它还要求
> `next.length <= 12`，而这个标签 21 字。
> **当初没查出来，有两个叠在一起的原因。** 一是验收只审了「碰到 `▶` 正文」的那 4 处——
> 照小分母去审，会正好在第 5、6 处上停下，而缺陷就在那里。
> 二是**这个缺陷不改变管线印出来的任何一个数**：实测（`tools/_diag-blocks.ts`，
> 把那一处错接手工补回去再逐项比）块数两边都是 **44**、标题集合完全相同、
> 39 个条目与 44 个块的 `sourceRef` **一行都没挪**。唯一的差别是
> `导入/车卡规则` 这一块的**正文里多了一个焊进来的章节标签**——
> 而正文正是喂给两个分类器的东西。没有任何计数会动，所以任何对数的验收都抓不到它。
> （先前这一段写的「带缺陷跑出来是 43 块」是推理出来的，量了之后不成立，已删。）
> 修法是在 `joinPages` 里加两条**只在页边界成立**的否决，`shouldJoin` 的页内语义一个字没动：
> 页顶的冒号收尾行一律不接（不看长度），上一页末行 ASCII 连续句点算句末。
> 为什么不并进共用的 `SENTENCE_END`：并进去之后逐字节比过全书 `cleanPageText` 输出，
> 变了 2 页 5 处——p15 四个结局标签不再被粘成一行（改好了），
> 但 p12 那段法语疯话被从句子中间劈开（改坏了，`...` 在那里是句内停顿）。
> 页内的 `...` 两种含义都有，页边界上（全书仅 p1 末行一处）只有句末那种。
> **p15 那 4 处是 `cleanPageText` 的一个独立潜在缺陷**（叙述被焊到 `Good End`/`Bad End`/`True End`
> 这些结构标签上，p15 的 6.0× 压缩比全书最高就是它），留给单独一轮 + 单独一份审计。

4 个条目的正文因此变完整，其中两处实质性：`防盗门的钥匙` 补回「不多见。」
（`item_12` 的截断症状消失）；`其他受害者的床位` 补回一整段，含 `极难的急救`、
`成功的力量` 这些真机制。

`捕兽夹` 仍然没有 `maimAtHpRatio`、硫酸陷阱仍然没有 `firstAid` —— **符合预期**，
那两处出自**同页**续句（根因 B），`joinPages` 只管跨页。

#### 一个意外发现：分类器的逐条输出不是独立的

改完之后精确率从 **9/17 变成 9/19**（多了 2 个误报：`受害者床位边上`、`中控台的开关`，
基准里都是 `Clue`）。而 `tools/_diag-joined.ts` 实测：**这两个条目的正文一个字都没变。**

我先据此判定「与 joinPages 无关，是采样漂」——**这个判断是错的**。
接着连跑 4 次，全部稳定在 9/19；而改之前两次都是 9/17。

真机制是：`buildItemPrompt` 把 37 个条目**塞进同一个 prompt**。
`joinPages` 改了 4 个条目的正文 → 整个 prompt 变了 → 模型对**其他**条目的判断跟着翻。

两条后果要记住：

1. **分类变化不能归因于正文发生变化的那个条目。** 想知道某处改动的影响，看整批分布，
   别看单条。
2. **拿一个文本处理改动去 A/B 一个批量分类器，本身是混淆的。** 要干净地测 `joinPages`
   的收益，得看条目正文的完整度（可确定性验证，如上面那 4 处），而不是看下游分类指标。

顺带修正一条更早的说法：同 prompt 下的采样方差**很小但不是零**——块分类的分布曾在两次跑之间
从 `npc 3 / rule 5` 变成 `npc 2 / rule 6`（挪了一个块）。物品那边 4 次跑完全一致。

### ⚠ 展示格式渗进输出契约——这是第三次（2026-09-02）

`extractKnownTitle`（`classify-sections.ts`）解决的是同一个模式的第三次
发作：**LLM 的输出里混进了给人看的展示格式，解析器只认一种字面形态，
一旦模型照抄了展示格式而不是纯数据，解析器整体判定"认不出"，表现成
"模型没干活"，实际是模型全做对了。**

搜过 `docs/notes/` 确认之前没有任何一条笔记用这个框架整理过它——
两次更早的实例只各自留在了自己的位置，没有被认成同一类：

1. **2026-08-19**（`classify-sections.ts` 自己的历史，`b1e84bc`）：
   prompt 里标题展示成 `【农场外围】`，模型照抄格式回来，当时的
   `normalizeKey` 只会裸标题，43 个块全部判"认不出"——解析出 0 条。
   修法：剥掉贴着字符串首尾的方括号。
2. **2026-08-29**（`todo-29`，`b267e906`）：LLM 正确判定
   `{"action":"talk",...}`，但裹在 ` ```json ` 围栏里，`intent.ts` 当时
   裸调 `JSON.parse(raw.trim())`，围栏直接让它抛异常——静默回落到
   regex 兜底，贪婪的 `/追/` 把"追问 NPC"命中成"chase"，一次对话
   请求变成一次战斗判定。修法：全仓六份"从 LLM 回答抠 JSON"的拷贝
   收敛到 `src/llm/json.ts` 的 `extractJson()`，统一做围栏剥离。
3. **2026-09-02**（`todo-51`，本轮）：模型这次把方括号标题连同后面
   一段摘录正文一起抄了回来，方括号不再贴着字符串结尾——
   "只剥首尾"这条第一次修法本身也不够宽，43 个块只解析出 1 条。
   修法：改成从键的任意位置抽取全部方括号片段，要求在已知标题里
   唯一命中才采纳。

三次的共同结构：**prompt 里为了让人读起来清楚而加的展示格式
（方括号强调、markdown 代码块），被模型原样带进了本该是纯数据的
输出里，而解析器最初都只认"最省事的那一种"字面形态**。第一次和
第三次甚至是同一个函数被同一类问题咬了两次——第一次修的是"方括号
贴在首尾"，第三次才发现"贴在首尾"本身就是个不必要的假设。

**可推广的判断**：约束"模型必须只输出纯 JSON、不要有多余文字"这句
prompt 指令，实测**从来没有被完全遵守过**——三次实例横跨两个不同的
模块、两种不同的"多余内容"（方括号强调、代码围栏），说明这不是
"这个 prompt 写得不够狠"的问题，是"LLM 输出格式天然有漂移，解析器
设计时就该假设它会漂移"。往后新写一个"从 LLM 回答里抠出结构化数据"
的解析器，起手就该按"入参可能带任意展示格式噪音，只要核心数据能
在噪音里唯一定位就该认出来"设计，不要等实跑撞见了第 N 次才加固——
这条经验本身已经跨两个模块发作过三次，没有理由认为第四次不会发生
在别的解析器上。

### 线索产出从 0 到 15——范围决策与第一版实测（2026-09-02）

todo-28 记的缺口：`build-scenes.ts` 把 `clues: []` 硬写死，
`build-items.ts:82` 又把分类器已经认出来的 clue 条目全部丢在地上——
两边都"没做错自己那一段"，只是没有任何模块接手 `classify-items.ts`
早就分出来的 clue 分类结果。线索是这个模组最大的一块内容（基准
32 条），管线走到摄取的最后一步却一直产不出一条，是目前最大的缺口。

**范围决策——为什么只产 name/description/revelation 三个字段**：
`Clue` 类型另外还有 `findMethods`/`unlocks`/`importance`/`hint`/
`failback`/`setStateVar` 六个字段，全都不产，理由不是"来不及"，是
"原文是散文，没有任何结构标记能确定性抽出这些判断"——`findMethods`
要的是"用什么技能、什么难度能找到它"，原文里这类信息经常混在场景
描述的正文里，不是独立成句的规则文本（陷阱机制之所以能用
`extract-trap.ts` 规则抽取，是因为原文写陷阱伤害/难度用的是骰子
表达式与"困难/极难成功"这类死板措辞，线索的"怎么找到"没有这种
形态）；`unlocks` 尤其不能碰——`clue_bedroom_diary.unlocks` 这个字段
的语义就是被误解过一次的真实事故（2c38d2c 修的卧室线索 bug：
`unlocks` 曾经被当成"自动连锁发现"来读，而模组数据写它的本意是
"前置门"，两种读法在这个字段上完全对立），管线自己去猜"A 解锁 B"
这种因果关系，猜错的后果比"不产"更重。`importance` 是必填枚举没有
"未知"选项，只能给最保守的占位值（`"color"`，不主动提示、不影响
流程）并在 `warnings` 里显式说明这不是真实评估——不是漏填，是"这个
字段类型不允许留空，只能选一个后果最小的默认值"。

**第一版实测（真实 PDF + 真实 LLM ecnu-plus，`analysis/ingest/
report.txt`，详细数字与方法论见 `build-clues.ts` 自己的文件头注释，
这里不重复摘抄，只记决策）**：产出 15 条，基准 32 条线索里只有 21 条
在评分口径表里有位置坐标（另外 11 条原文没有对应的 ▶ 条目，这套
按位置比对的方法本来就够不到，不算"漏了"），按坐标覆盖 12/21，
精确率 11/15。**这是第一版，数字难看是预期内的**——评分口径的边界
（绝不进 prompt）本轮没有碰过，没有为了让数字好看去调 prompt。

**可推广的判断**：一个字段"型要求非空"（如 `importance` 这类枚举）
不等于"这个信息现在就能确定性产出"——两者是完全不同的两件事，前者
是类型系统的约束，后者是数据源本身够不够。遇到这种情形，选一个
"后果最小"的默认值（这里是"不主动提示"而不是"核心线索"）并显式
在 warnings 里承认它是占位，比因为类型不让留空就顺手编一个"看起来
认真评估过"的值更诚实——占位与编造的区别，就在于占位会被下一个人
一眼看出"这不是真的"，编造不会。

### era / 部分 meta 抽取——先划清「结构信号」与「编辑判断」的边界（2026-09-02）

`assemble-module.ts` 曾经把 `era`/`summary`/`meta` 整体硬编码成空，
理由是"没做，不猜"。但这三者不是同一种难度：`era`（"1921 年"）、
`meta.playerCount`（"人数为 2~3 人"）、`meta.expectedDuration`
（"长度中短"）在原文里都是"标签词 + 紧跟的值"这种结构，位置信号
够硬，能确定性抽——新增的 `src/ingest/extract-header-meta.ts` 就做
这三个，真实管线跑通后三个字段都与手写基准逐字一致（`era: "1921"`、
`playerCount: "2~3"`、`expectedDuration: "中短"`）。

`summary` 与 `meta.triggerWarnings` 没有这种标签词，留空。基准的
`summary` 是前言段落里连续三句话的原文摘抄，但"该摘哪几句"是编辑
判断，没有位置信号能确定该从哪儿切到哪儿；`triggerWarnings` 同理，
基准把原文一整句"可能包含……与……"拆成了两条独立的警示语，这个
拆分本身也是编辑判断，不是结构抽取。两个字段都在 warnings 里显式
说明"不是没做到，是没有可以确定性抽的信号"，不强行给一个看起来
像模像样但实际是猜的值。

开发过程中一次真实的过拟合教训：`meta.expectedDuration` 最初的正则
是"长度后面跟着的几个字"，结果被"没有提到长度的正文"这种句子里
偶然出现的"长度"一词命中，抓出了后面几个无关字——「长度」是常见
汉语词，不是只在时长标记里出现。改法不是让正则更"聪明"，是收窄成
一张封闭的时长描述词表（中短/中长/较长/较短/长/中/短……），词表外
的一律不认。**可推广的判断**：一个词是否够格当"结构信号"，不能只
看它是否出现在原文里，还要看这个词本身有没有歧义——常见词即使
出现在正确的位置模式里，命中率也可能是假的，收窄到封闭词表比放宽
正则更安全。

### 叙事层立项——为什么"允许编"要单独开一条通道（todo-52，2026-09-02）

摄取管线到 todo-28（线索）为止，产的都是"抽取"：原文里有什么就
搬什么，没有就留空。但基准数据里还有一批字段——`Scene.
openingAtmosphere`、`prologue.lines`、`partySetup`、`epilogues`、
`narrative.entities`——逐字核对过原文没有任何对应文本（"一封拜托的
信""拍打""皮球""夜色中，两人回到地面"在 `tools/modules/raw/` 全部
`MISS`），这些字段的存在本身就要求"创作"，不是"没抽干净"。摄取
管线到目前为止的每一条纪律都是"一个字都不编"（`assemble-module.ts`
文件头），这批字段第一次要求反过来——不是取消那条纪律，是要开一条
新的、单独的通道，纪律本身不变。

这条 todo 只做"立项"：把范围与已经定下的约束写成正式记录，不含
实现（实现是下一轮的事）。核心分工写在 todo-52 里，这里只记为什么
这么分：

- **`sourceRef` 方案 C**（有依据填依据、纯创作显式登记）而不是让
  纯创作也编一个假 `sourceRef`——假 `sourceRef` 比留空更危险，它会
  让下一个人以为这段创作是从原文哪里抄来的，去查证时扑空。

- **三档约束里，只有前两档进管线当门禁**。第一档（禁止生成文本里
  出现原文没有的专名/术语）与第二档（生成文本提到的可交互对象
  称呼必须能被 `decideClueMatch` 命中）都是能写成确定性判据的
  东西——第二档尤其是"培养缸"那次事故（`docs/notes/engine.md`
  「引擎教了玩家一个自己不认识的词——这是第二次」）的机器化版：
  那次是人写的叙事教会了玩家一个匹配键不认识的词，只能靠实跑的
  自然语句撞见；这次生成叙事时手上就有当前场景的线索集，能在
  生成的那一刻直接断言，不用等到实跑。第三档（语义层面"这句话
  是否与设定矛盾"这类蕴含扫描）做不到这种确定性，只能是开发期
  工具，因为它最终要人来裁决对错——这与 `docs/handoff.md:59`
  早就定下的"只能告警、不能当 preflight 门禁"是同一条纪律，不是
  为这一轮新开的例外。

- **创作层产物不进校准 diff**。`calibrate.ts` 的 diff 逻辑是给
  抽取类字段用的——生成的叙事文本逐字不会和基准一样，硬塞进 diff
  只会让 `report.txt` 的 changed 数暴涨，把线索/场景这些真正的抽取
  差异淹没掉。这条边界必须在实现那一轮的第一个 commit 就做对，
  不能等数字已经跑歪了再回头查是不是隔离漏了。

**可推广的判断**：一条"允许编"的新纪律不是对旧纪律的推翻，而是
需要自己单独的一套确定性判据——旧纪律（不编）之所以能一直守住，
是因为每次想放宽它，都先问"有没有能守住底线的机器判据"，不是
先问"要不要放宽"。这条 todo 记的就是这次问出来的答案，实现时
直接照做，不必重新论证。

### 叙事层第一版——0/3 采纳，三档约束真的拦下了三种不同的真实错误（2026-09-03）

todo-52 立项之后的实现轮：新增 `src/ingest/build-narrative.ts` +
`src/ingest/narrative-guard.ts`。**范围比立项时又收窄了一次**——只产
`Scene.openingAtmosphere`/`prologue.lines`/`partySetup` 三样，`epilogues`
与 `narrative.entities` 本轮没做，理由与 `build-clues.ts` 当初不产
`unlocks` 同一种判断：这两个字段都要求生成端引用具体的线索/场景 id，
而这些 id（`item_03` 这类内部句柄）只有在同一次摄取跑完之后才存在，
写 prompt 那一刻 LLM 根本不知道它们长什么样——硬让它编，编出来的 id
要么压根不存在（死数据），要么"看起来对但没人验证过"，比留空更危险。

**三档约束的分工**（立项时定的，实现时没有改）：第一档
（`findFabricatedTerms`，复用 `three-way-audit.ts` 的
`extractBracketTerms`/`termAppearsInCorpus`）与第二档
（`findUnresolvedObjectMentions`，复用 `decideClueMatch`）接进管线当
门禁；`checkNarrationText`（`world-constraint.ts`）另接一层，与 KP
叙事共用；第三档（语义蕴含扫描）按立项决策不进管线。任何一档不过，
整批生成结果一律不采纳——不是"部分产出、能用的先用上"。

**真实管线跑了三轮（真实 PDF + 真实 LLM ecnu-plus），三轮都被拦下，
且是三种不同的真实失败**（不是构造出来验证判据的用例，是生成时自己
撞出来的）：
1. 第一档拦下：`partySetup.context` 里写了"艾德里安……正在进行某种
   危险的【生化仪式】"——原文 0 命中。同一次回复里还有一条
   `objectMentions` 声明指代线索 id `gabi_pistol`，这个 id 当次摄取
   根本不存在——说明当时 prompt 没把真实线索列表喂给模型，它只能编。
2. 改进前的最后一轮：第二档拦下，同样是编 id（`grill_residue`，
   同样不存在）。
3. 把每个场景真实的"线索 id→名字"列表喂给模型之后：第二档仍然拦下，
   但换了一种更细的失败模式——这次 id 是真的（`item_28`，对应基准
   线索"其他受害者的床位"），但生成文本用"那些被仪器罩住的人"这句
   复述指代它，`decideClueMatch` 认不出这句话对应 `item_28`（线索的
   `matchTexts` 目前只有名字本身）。**这正是"培养缸"事故**（`docs/notes/engine.md`「⚠ 引擎教了玩家一个自己不认识的词——这是第二次（2026-09-02）」，commit 7d9e6f1）**的原始形状**——不是编个不存在的东西，
   是用一个新措辞称呼一个真实存在的对象，而匹配器认不出来。三档约束
   设计时设想的正是这类问题，真实撞见比构造用例更有说服力。

**第一版实测 0/3 采纳，如实记录，没有为了让这个数字好看去放宽门禁
或调整 prompt 到"更容易过"**——与 `build-clues.ts`"数字难看是预期
内的"是同一条纪律。三轮之后把线索列表喂给了模型（见实测②③的对比），
这是唯一做的一处 prompt 调整，理由是"没有列表，第二档的声明只能是
瞎猜"，不是"为了让判据更容易过"——调整前后判据本身一个字都没有动。

**隔离校准验证**：三轮实跑的场景/物品 diff（`changed` 79、`missing`
78 三轮完全一致，`extra` 在 29~30 之间浮动）与本轮改动前的历史数字
同口径——创作层无论产出还是被拒，都没有影响到抽取层的既有指标。
机制不是"算完 diff 之后把创作层字段摘掉"，是编排顺序本身：
`scripts/ingest/run.ts` 里 `buildNarrative()` 排在 `diffValues()`
**之后**调用，喂给 diff 的那份 `scenes` 从头到尾没见过
`openingAtmosphere` 这个字段，没有"漏摘"的可能。

**可复现性——生成层的不确定性与抽取层的不确定性不是同一件事**：
抽取层的不确定性（`classify-sections.ts`/`classify-items.ts` 跨轮
分类结果小幅波动）已经在本文档别处记录过，是"同一个问题该有的答案
每次可能因为模型答题的边界情况判得不一样而略微不同"；创作层的
不确定性是另一类——**同一份 PDF 每次生成的叙事文本内容本身就不同**
（措辞、要不要给某个场景写 openingAtmosphere、要不要声明
objectMentions 全部随机），门禁能不能通过也因此每次不同——三轮里
两次栽在"编不存在的 id"，一次栽在"真实 id 但措辞对不上"，这三种
结果都可能在下一轮重跑时换成别的失败模式，或者侥幸全部通过。
**下一个人看到"这轮又没通过"不该以为管线坏了**——先看 warnings 里
是哪一档拦的、原始回复长什么样（`analysis/ingest/classify-raw.txt`
的"创作层"段），再判断是否需要继续调整 prompt。样本：3 轮，
model：ecnu-plus，日期：2026-09-03（同 `probe-llm-intent.md` 的
记录惯例：结论必须带模型名/日期/样本数，不能当常量用）。

### A 组：四项遗留问题逐条查清，不留"待定"（2026-09-03）

叙事层收尾之后还剩四个没有明确答案的问题，逐条查证据、给答案——
"不允许不做判定"，查完发现不能做也要把理由钉死，不能挂着"以后再说"。

**A1：`Scene.atmosphere` 能不能确定性切分？不能。**
起初的假设是：原文里"引号框住的话"是读给玩家听的 box text（对应
`description`），引号外紧跟着的一段是 KP 专用笔记（对应
`atmosphere`）——`weisen_bar`/`hospital`/`adrian_bedroom` 三个场景
确实完全符合这个假设。但再查三个反例，这条规则站不住：
- `tricam_house`：引号外有两段话，只有第二段（"因为考虑到终局的
  那一幕……"）变成了 atmosphere，第一段（"这是调查员开幕的场景，在
  特里坎家的别墅中没有任何有用的信息……"）整段被弃用，两个字段都没有
  它——如果规则是"引号外的都是 atmosphere"，这段会被误收。
- `newsstand`（报亭）：全文没有一处引号，`description`（"调查员可以
  通过报亭购买报纸获取信息。"）与 `atmosphere`（"报亭老板认为翻找旧
  报纸太麻烦……"）都是对同一段无引号原文的改写摘要——没有引号可以
  拿来切分，两个字段的边界纯粹是人读完之后自己划的。
- `police_station`：引号外有一大段可操作性文字（"调查员也有可能会
  直接来到警察局询问……"），但基准里这个场景压根没有 atmosphere 字段
  ——不是没东西可切，是人工判断这段不算"环境色彩"（它是纯粹的线索
  分发逻辑，不是场景描写）。

三个反例覆盖三种不同的失效方式（多段选一/没有引号可切/有内容但人工
弃用），结论是"这段话算不算环境色彩"是编辑判断，不是可以从文本结构
直接读出来的东西。摄取管线维持现状：`build-scenes.ts` 不产
`atmosphere`，`three-way-audit.ts` 的 `FIELD_OMISSION_REGISTRY` 对
`.atmosphere` 的裁决（"漏抽而非臆造"）依然成立——只是现在多了一句
"漏抽是真的，但补不上，因为切分点本身就没有客观答案"。

**A2：`ModuleItem.revelation` 的现状——确认未产，且不该产。**
`build-items.ts` 只写 `description`/`type`，从没写过 `revelation`
（`report.txt` 报的 `items[photo_farm].revelation`/
`items[old_document].revelation` missing 都是这个原因）。基准 10 个
物品里也只有 2 个带这个可选字段。核对原文之后发现两个样本证据强度
完全不同：`old_document.revelation`（"通篇为法语所写。阅读导致
sc1/1d3+1，研究2周可学会「米-戈联络术」且CM+3。"）**部分**有依据
——"通篇为法语所写"与后面的数值都在原文同一个 ▶ 条目正文的尾段
（section_11.txt:37-39），只是被基准作者拆成了 description 前段
与 revelation 后段两个字段；但 `photo_farm.revelation`（"照片背面
写着农场的地址坐标。"）**在全部 18 个原文切片里 0 命中**——这不是
抽取遗漏，是基准作者自己想象出来的补充设定。一个字段的两个仅有样本，
一个"能切但摄取管线现在不切"，一个"压根不是从原文来的"，比 A1 的
证据还要更差——维持不产，不新增任何抽取逻辑去猜这道边界在哪。

**A3：线索为什么只挂在 7/23 个场景上？不是归属 bug，是原文分布。**
